РОЗДІЛ 4. РЕАЛІЗАЦІЯ ТА ТЕСТУВАННЯ МОБІЛЬНОГО ЗАСТОСУНКУ HIKORA
4.1. Реалізація серверної частини
Серверну частину застосунку розгорнуто на хмарній платформі Supabase [12] без використання окремого VPS-сервера. База даних PostgreSQL [13] містить 15 таблиць та одне представлення profile_stats з увімкненим механізмом Row Level Security [16] для розмежування доступу між користувачами. Автентифікацію реалізовано через Supabase Auth з підтримкою входу через email і пароль та Google OAuth. Серверна логіка, що потребує захищеного доступу до зовнішніх API або атомарного виконання операцій, реалізована через 10 Edge Functions на базі Deno.
4.1.1. Реалізація серверних функцій
Серверні функції виконують роль BFF-шару між мобільним клієнтом і зовнішніми сервісами. Кожна функція приймає запит від клієнта, виконує необхідну логіку на сервері та повертає результат. Ключ OPENAI_API_KEY та інші секрети зберігаються виключно в Supabase Secrets і не потрапляють у клієнтський код.
Функція recommend-routes формує персоналізовані рекомендації маршрутів через OpenAI API [20]. За відсутності ключа повертає source: profile і список від резервного алгоритму rankRoutesByProfile. Уривок коду виклику функції:
Future<({List<Map<String, String>> items, String source})>
fetchRecommendations() async {
final response = await _client.functions.invoke(
'recommend-routes', body: {},
);
final data = _asMap(response.data);
final source = data?['source']?.toString() ?? 'profile';
return (items: out, source: source);
}
Функція ai-chat реалізує діалоговий ШІ-консультант з історією повідомлень. Функція weather отримує прогноз від OpenWeatherMap. Функція save-route виконує атомарне збереження маршруту з точками. Функція route-hike будує трек через GraphHopper [21] або OSRM. Функції geosearch та poi-nearby обслуговують геопошук і точки інтересу. Функція prepare-offline-route підготовляє лінію шляху для офлайн-пакета. Функція trip-actions обробляє заявки групових походів. Функція trip-chat забезпечує надсилання повідомлень у чаті.
4.1.2. Реалізація доступу до даних
Обмін даними між клієнтом і сервером відбувається через Supabase Dart SDK (PostgREST): репозиторії формують запити .from('table').select() / .eq() / .upsert(), результати перетворюються на Dart-моделі вручну в шарі data за патерном Repository [14] без використання ORM. Для збереження маршруту разом із точками використовується Edge Function save-route. Уривок коду:
final data = await _api.invoke(
'save-route',
body: {
'action': 'create', 'title': title,
'route_type': routeType, 'difficulty': difficulty,
'is_public': isPublic, 'points': points,
},
timeout: const Duration(seconds: 120),
);
return data['route_id'].toString();
Для оновлення списку походів і сповіщень використовується Supabase Realtime через WebSocket-підписки. Завантажені офлайн-маршрути дублюються записом у таблиці offline_routes, файли пакета зберігаються у файловій системі пристрою через path_provider. Аватари зберігаються в Supabase Storage (bucket avatars). Уривок коду запису офлайн-маршруту в БД:
await _client.from('offline_routes').upsert({
'user_id': userId,
'route_id': routeId,
'downloaded_at': DateTime.now().toUtc().toIso8601String(),
'tile_cache_mb': tileCacheMb,
});
4.2. Реалізація клієнтської частини
Клієнтський застосунок реалізовано мовою Dart у фреймворку Flutter SDK 3.0+ [11]. Проєкт організовано за принципом feature-first: каталог lib/features/ містить модулі auth, routes, navigation, weather, trips, journal, profile, ai, home. Кожен модуль поділено на шари presentation, data та domain. Спільна інфраструктура зосереджена в lib/core/. Управління станом реалізовано бібліотекою flutter_riverpod [23], навігація — через go_router [24]. Структуру клієнтської частини наведено у додатку Б.
4.2.1. Реалізація навігації та захисту маршрутів
Навігацію між екранами реалізовано через go_router [24] із захистом маршрутів на основі стану сесії. Маршрутизатор перевіряє наявність активного JWT-токену та заповненість фізичного профілю: якщо після OAuth-входу профіль не заповнено, користувач перенаправляється на /register?oauth=1. Уривок коду функції redirect:
redirect: (context, state) async {
final session = Supabase.instance.client.auth.currentSession;
final isLoggedIn = session != null;
if (!isLoggedIn) {
if (isLoginRoute || isRegisterRoute) return null;
return '/login';
}
final needsPhysical = await _needsPhysicalProfile(userId);
if (needsPhysical) {
if (isRegisterRoute) return null;
return '/register?oauth=1';
}
return null;
},
Для офлайн-навігації маршрутизатор передає параметр offline=true до NavigationScreen, що вимикає всі мережеві запити. Перевірку заповнення профілю реалізовано через запит поля age з таблиці profiles.
4.2.2. Реалізація маршрутів, геопошуку та збереження
Каталог маршрутів завантажується через RoutesRepository з фільтрацією за складністю, типом (circular / linear / radial / combined), тривалістю, набором висоти та пошуком за назвою. Точки завантажуються окремим запитом у getRouteDetail. Уривок коду формування запиту:
dynamic query = _client.from('routes').select().eq('is_public', true);
if (search != null && search.isNotEmpty)
query = query.ilike('title', '%$search%');
if (difficulty != null && difficulty != 'all')
query = query.eq('difficulty', difficulty);
if (routeType != null && routeType != 'all')
query = query.eq('route_type', routeType);
if (durationMax != null && durationMax > 0)
query = query.lte('duration_h', durationMax);
if (ascentMax != null && ascentMax > 0)
query = query.lte('ascent_m', ascentMax);
final data = await query.order('created_at', ascending: false);
Геопошук виконується через Edge Function geosearch. Трек будується через route-hike на основі GraphHopper [21] або OSRM як резерв; за недоступності Edge RoutingRepository звертається до API через Dio. Збереження маршруту разом із точками виконується атомарно через save-route.
4.2.3. Реалізація офлайн-карт та навігації
Сервіс OfflineMapService реалізує метод downloadRouteMap, що повертає потік прогресу. Лінію шляху підготовляє Edge Function prepare-offline-route. У каталозі offline_tiles/{routeId} зберігаються тайли OSM (zoom 11–16), route_path.json, map_meta.json та маркер .complete. Тайли завантажуються через Dio. Уривок коду завантаження пакета:
Stream<OfflineMapDownloadProgress> downloadRouteMap(
RouteDetail detail, {required List<LatLng> pathPolyline},
) async* {
final dir = await _routeDir(detail.route.id);
// завантаження тайлів OSM (zoom 11-16) через Dio
await _writePath(detail.route.id, OfflineRoutePath(
polyline: pathPolyline, waypoints: detail.waypoints,
));
await _writeMeta(detail.route.id, _MapMeta(/* метадані */));
await marker.writeAsString('1', flush: true); // .complete
}
Реалізовано два режими навігації: класична онлайн-навігація з екрана деталей маршруту (перебудова треку через route-hike, POI через poi-nearby) та офлайн-only режим з вкладки «Офлайн» (offline=true). На екрані відображається GPS-позиція з обертанням маркера за курсом, пройдена частина (сірий) та залишкова (зелений). При відхиленні — SnackBar і перебудова треку.
Після завершення завантаження пакета запис зберігається в таблиці offline_routes:
final pathPolyline = await resolveRoutePathPolyline(widget.detail, routingRepo);
await for (final progress in offlineService.downloadRouteMap(
widget.detail, pathPolyline: pathPolyline,
)) { setState(() => _progress = progress.fraction); }
final sizeMb = await offlineService.cacheSizeMb(widget.routeId);
await routesRepo.saveOfflineRoute(widget.routeId, sizeMb);
4.2.4. Реалізація групових походів
Створення та редагування походу реалізовано через Edge Function trip-actions (дії create, update, apply, decide, cancel). Уривок коду створення:
final data = await _invoke({
'action': 'create', 'title': title,
'description': description, 'meeting_point': meetingPoint,
'max_members': maxMembers, 'start_date': startDate,
'end_date': endDate,
if (routeId != null) 'route_id': routeId,
});
Повідомлення у чаті надсилаються через Edge Function trip-chat і зберігаються в таблиці messages з RLS-доступом лише для approved-учасників. Список походів оновлюється через Supabase Realtime.
4.2.5. Реалізація погоди, журналу та профілю
WeatherRepository викликає Edge Function weather, яка звертається до OpenWeatherMap на сервері. Доступні екрани /weather та погода на маршруті. Уривок коду:
final data = await _api.invoke(
'weather',
body: {'action': 'both', 'lat': lat, 'lon': lon},
);
Журнал реалізовано через таблиці journal_entries та journal_photos; після завершення маршруту система пропонує діалог збереження запису. Профіль охоплює редагування даних, статистику через profile_stats, досягнення з автонарахуванням тригерами в БД, налаштування та вкладку «Мої маршрути». Вхід через Google OAuth реалізовано через Supabase Auth:
final launched = await Supabase.instance.client.auth.signInWithOAuth(
OAuthProvider.google,
redirectTo: kIsWeb ? null : 'io.supabase.flutter://login-callback/',
);
4.3. Результати реалізації застосунку
У цьому підрозділі наведено результати реалізації застосунку у вигляді демонстрації його роботи. Розглянуто основні сценарії використання: авторизацію, планування маршруту, навігацію, групові походи та ведення журналу. Інструкцію користувача подано у додатку Л.
4.3.1. Демонстрація авторизації та налаштування профілю
Робота із застосунком розпочинається з екрана авторизації (рис. 4.1), де користувач вводить email і пароль або входить через Google. Після першої реєстрації через Google маршрутизатор перевіряє заповненість профілю та перенаправляє на екран первинного налаштування, де вказуються вік, рівень підготовки та медичні обмеження.
Рис. 4.1. Екран авторизації застосунку
4.3.2. Демонстрація головного екрану та ШІ-рекомендацій
На головному екрані відображається блок персоналізованих рекомендацій маршрутів та вікно ШІ-консультанта (рис. 4.2). Рекомендації підбираються через Edge Function recommend-routes з урахуванням профілю. За відсутності OPENAI_API_KEY — резервний алгоритм (source: profile).
Рис. 4.2. Головний екран з рекомендаціями та ШІ-консультантом
4.3.3. Демонстрація роботи з маршрутами
Каталог маршрутів підтримує пошук та фільтрацію. При відкритті деталей маршруту відображається інтерактивна карта з треком, перелік ключових точок та кнопки завантаження офлайн-пакета і початку навігації (рис. 4.3).
Рис. 4.3. Екран деталей маршруту
4.3.4. Демонстрація навігації
Навігаційний екран (рис. 4.4) відображає GPS-позицію мандрівника, пройдений та залишковий трек, точки інтересу. При відхиленні система перебудовує трек в онлайн-режимі або продовжує за офлайн-пакетом.
Рис. 4.4. Екран навігації під час активного походу
4.3.5. Демонстрація групових походів
Розділ групових походів дозволяє переглядати заходи, подавати заявки та спілкуватись у груповому чаті після підтвердження участі (рис. 4.5). Організатор переглядає список заявок та ухвалює рішення.
Рис. 4.5. Екран групових походів та чату
Після завершення навігації застосунок пропонує зберегти запис у журнал зі статистикою, нотатками та фотографіями (рис. 4.6). Статистика агрегується через profile_stats і відображається графіками на екрані профілю.

4.4. Результати тестування застосунку
Тестування проведено з метою перевірки відповідності специфікації вимог, виявлення дефектів та підтвердження коректності реалізованих рішень. Процес охопив два етапи: розроблення тестів та виконання тестування з аналізом результатів. Застосовано три види тестування: функціональне, тестування безпеки та орієнтовне тестування продуктивності.
4.4.1. Розробка тестів
Під час розроблення тестів спроєктовано тестові випадки для кожного виду тестування. Кожен тестовий випадок містить передумови, вхідні дані, послідовність кроків та очікуваний результат.

4.4.5. Метрики покриття та критерій прийняття
За результатами тестування оцінено повноту покриття. Усі заплановані тестові випадки для двох видів тестування розроблено та виконано. Функціональними тестами охоплено всі варіанти використання специфікації. Виявлені під час тестування три дефекти усунено:
–	некоректне закриття списку підказок OSM після вибору місця — усунено додаванням FocusScope.unfocus();
–	відсутність обертання маркера GPS — усунено передачею параметра heading з geolocator;
–	некоректний автоперехід в офлайн-режим за активного з'єднання — усунено розділенням двох режимів навігації.
Критеріями успішного завершення тестування визначено такі умови:
–	усі заплановані тестові випадки функціонального тестування та тестування безпеки розроблено та виконано;
–	усі варіанти використання специфікації покриті функціональними тестами;
–	виявлені під час тестування дефекти усунено або визнано некритичними.
Усі визначені критерії виконано повною мірою. Усі тестові випадки пройдено успішно, критичних дефектів не виявлено.
4.5. Висновки до розділу 4
У четвертому розділі описано реалізацію та тестування мобільного застосунку Hikora. Серверну частину розгорнуто на Supabase (15 таблиць, profile_stats) з 10 Edge Functions як BFF-шаром. Клієнтську частину реалізовано на Flutter за принципом feature-first. Реалізовано вісім підсистем: автентифікацію, маршрути з геопошуком, офлайн-навігацію з двома режимами, погоду, групові походи з чатом, ШІ-рекомендації, журнал і досягнення.
Проведено функціональне тестування за 12 тестовими випадками у 6 модулях, тестування безпеки та орієнтовне тестування продуктивності. Усі функціональні вимоги специфікації розділу 2 підтверджено, виявлені три дефекти усунено. У поточній версії не реалізовано UI для route_ratings та saved_routes; мобільні push-сповіщення не використовуються. Детальні тестові випадки наведено у додатках М та Н, інструкція користувача — у додатку Л.
Додаток Л. Інструкція користувача
Л.1. Компоненти програмного забезпечення
Hikora — мобільний застосунок для планування гірських походів, реалізований за клієнт-серверною архітектурою. Клієнтська частина розроблена на Flutter [11] з єдиною кодовою базою для Android та iOS. Серверна частина розгорнута на хмарній платформі Supabase [12] без окремого VPS-сервера.
Мінімальні вимоги до пристрою:
–	операційна система — Android 8.0 і вище або iOS 14.0 і вище;
–	оперативна пам'ять — від 2 ГБ;
–	процесор — щонайменше двоядерний від 1.8 ГГц;
–	вільний простір — від 500 МБ для офлайн-пакетів карт;
–	GPS-модуль — для навігаційних функцій;
–	мережеве підключення (3G/4G/5G або Wi-Fi) — для більшості функцій.

Л.2. Встановлення програмного забезпечення
Для встановлення застосунку на Android-пристрій завантажте APK-файл за посиланням, наданим розробником, та дозвольте встановлення з невідомих джерел у налаштуваннях пристрою. Для iOS встановлення виконується через TestFlight або App Store згідно з інструкцією розробника.
Після встановлення та запуску надайте застосунку наступні дозволи:
–	доступ до геолокації — для GPS-навігації;
–	доступ до камери та галереї — для фотографій у журналі та аватара профілю.
Л.3. Налаштування програмного забезпечення
Після першого запуску виконайте такі кроки:
–	оберіть спосіб реєстрації — через email і пароль або через обліковий запис Google;
–	заповніть фізичний профіль — вік, рівень підготовки, медичні обмеження та уподобання щодо складності й тривалості маршрутів;
–	за бажанням завантажте аватар у розділі редагування профілю.
Параметри застосунку (сповіщення, одиниці вимірювання) доступні в розділі «Налаштування».
Л.4. Базові функції програмного забезпечення
Л.4.1. Планування маршруту
Для підбору готового маршруту перейдіть до вкладки «Маршрути», скористайтеся пошуком за назвою або фільтрами за складністю, типом, тривалістю та набором висоти. Відкрийте картку маршруту для перегляду деталей: карти, точок, опису та прогнозу погоди.
Для створення власного маршруту натисніть кнопку додавання у каталозі. В редакторі вкажіть точки маршруту — геопошук допоможе знайти назви місць і вершин. Система автоматично розрахує протяжність, підйом та орієнтовний час. Після збереження маршрут з'явиться у вашому каталозі.
Л.4.2. Завантаження офлайн-карти
Для використання навігації без мережевого підключення заздалегідь завантажте офлайн-пакет маршруту. Для цього відкрийте деталі маршруту та натисніть «Завантажити карту офлайн». Після завершення завантаження маршрут з'явиться у вкладці «Офлайн» розділу «Мої маршрути».
Л.4.3. Навігація
Для запуску онлайн-навігації відкрийте деталі маршруту та натисніть «Почати проходження». На екрані відображатиметься поточна GPS-позиція, пройдений та залишковий трек. При відхиленні від маршруту система автоматично перебудує трек.
Для офлайн-навігації перейдіть до Профіль → Мої маршрути → вкладка «Офлайн» та оберіть завантажений маршрут. Навігація виконується без жодних мережевих запитів. Після завершення походу застосунок запропонує зберегти запис у журнал.
Л.4.4. Групові походи
Для організації групового походу перейдіть до вкладки «Групи» та натисніть кнопку створення. Заповніть форму: оберіть маршрут, вкажіть дати, місце збору, опис та ліміт учасників. Після публікації охочі можуть подати заявку. Як організатор переглядайте профілі заявників та схвалюйте або відхиляйте їх. Підтверджені учасники отримують доступ до групового чату.
Для приєднання до існуючого походу знайдіть його у списку та натисніть «Подати заявку». Після схвалення організатором ви отримаєте доступ до чату та деталей походу.
Л.4.5. Журнал та статистика
Після завершення навігації застосунок автоматично запропонує зберегти запис у журнал із заповненими метриками. Додайте нотатки та фотографії. Перегляд журналу доступний із головного екрану або розділу профілю.
Статистика (загальна кількість походів, відстань, підйом) відображається на екрані статистики та оновлюється автоматично. Досягнення нараховуються при досягненні порогових показників.
