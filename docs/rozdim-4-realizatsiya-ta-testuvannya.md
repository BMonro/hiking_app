# РОЗДІЛ 4. РЕАЛІЗАЦІЯ ТА ТЕСТУВАННЯ МОБІЛЬНОГО ЗАСТОСУНКУ HIKORA

*Чернетка структури для `rozd4_hikora.docx` за методичкою §3.12: реалізація **поступово** (БД → бекенд → клієнт), тестування **функціональне → безпека (+ MobSF) → навантаження**.*

---

## 4.1. Реалізація системи (поступово: від бази даних до застосунку)

Реалізацію виконано **послідовними етапами**: спочатку схема даних і політики доступу, потім хмарний бекенд Supabase, шар Edge Functions, і лише після цього — мобільний клієнт Flutter. Такий порядок відповідає архітектурі з розділу 3 і спрощує перевірку кожного шару окремо.

**Рис. 4.0** (рекомендовано) — ланцюг етапів: *PostgreSQL + RLS → Supabase (Auth, Storage, Realtime) → Edge Functions → Flutter-клієнт*.

---

### 4.1.1. Етап 1. База даних PostgreSQL

На платформі Supabase розгорнуто реляційну БД **PostgreSQL** з нормалізованою схемою (розділ 3): **15 таблиць** та представлення **`profile_stats`**.

| Група сутностей | Таблиці |
|-----------------|---------|
| Користувач | `profiles`, `profile_health_conditions` |
| Маршрути | `routes`, `route_points`, `route_ratings`, `saved_routes`, `offline_routes` |
| Походи | `trips`, `trip_participants`, `messages` |
| Журнал | `journal_entries`, `journal_photos` |
| Гейміфікація | `achievements`, `user_achievements` |
| Сервіс | `notifications` |

**Row Level Security (RLS)** увімкнено на всіх таблицях: користувач бачить і змінює лише «свої» або публічні дані (маршрути `is_public`, учасники походів `approved` тощо). Облікові записи — у **`auth.users`** (Supabase Auth), профіль — `profiles.id` → `auth.users.id`.

Додатково виконано:
- SQL-політики Storage для bucket **`avatars`** (`storage_avatars_policies.sql`);
- тригери нарахування досягнень (`achievements_auto_grant.sql`);
- тестове наповнення **`seed_data.sql`** (маршрути в Карпатах, досягнення).

*Повна схема — розділ 3 / додаток до БД; у §4.1 достатньо посилання та таблиці груп.*

---

### 4.1.2. Етап 2. Підключення бекенду (платформа Supabase)

Після створення схеми БД налаштовано **проєкт Supabase** (URL, `anon` key для клієнта, `service_role` лише на сервері / у скриптах тестування, не в APK).

| Сервіс Supabase | Роль у Hikora |
|-----------------|---------------|
| **PostgreSQL** | Зберігання всіх бізнес-даних |
| **Auth** | Email/пароль, Google OAuth, JWT-сесії |
| **PostgREST** | REST API до таблиць (через Dart SDK) |
| **Storage** | Фото аватарів, вкладення журналу |
| **Realtime** | Оновлення походів, заявок, чату, сповіщень |
| **Edge Functions** | BFF до зовнішніх API (наступний етап) |

Окремий VPS не використовується: серверна логіка зосереджена в керованій платформі, що зменшує витрати на адміністрування.

---

### 4.1.3. Етап 3. Edge Functions (серверна бізнес-логіка / BFF)

Реалізовано **10 Edge Functions** (Deno). Клієнт **не** звертається напряму до OpenAI, GraphHopper, OpenWeatherMap з секретними ключами — лише до Supabase з JWT.

| Функція | Призначення |
|---------|-------------|
| `save-route` | Збереження маршруту: метрики, GeoJSON (GraphHopper/OSRM), точки |
| `route-hike` | Пішохідна маршрутизація на сервері |
| `prepare-offline-route` | Полілінія для офлайн-пакета |
| `recommend-routes` | Рекомендації (OpenAI або `rankRoutesByProfile`) |
| `ai-chat` | Діалоговий консультант |
| `weather` | Погода (OpenWeatherMap) |
| `geosearch` | Геопошук (Nominatim/Overpass) |
| `poi-nearby` | POI на карті |
| `trip-actions` | CRUD походів, заявки `apply` / `decide` |
| `trip-chat` | Список/відправка повідомлень чату |

**Фрагмент `save-route`** (обчислення метрик і збереження) — у тексті розділу або **Додаток** (фрагмент з `supabase/functions/save-route/`).

Секрети (`OPENAI_API_KEY`, ключі маршрутизації) — у **Supabase Secrets**, не в репозиторії клієнта.

---

### 4.1.4. Етап 4. Обмін даними сервера з клієнтом (контракт API)

До підключення UI зафіксовано **контракт** взаємодії:

1. **Авторизація** — `POST /auth/v1/token` → JWT у заголовку `Authorization: Bearer …`.
2. **Табличні дані** — Supabase Dart SDK: `.from('routes').select()…` у класах **Repository** (`lib/features/*/data/`), без ORM.
3. **Складна логіка / зовнішні API** — `BackendApi.invoke('function-name', body)` → HTTPS до `/functions/v1/…`.
4. **Файли** — `Storage` (аватари: `avatars/{userId}-avatar.jpg`).
5. **Офлайн** — метадані в `offline_routes`; файли тайлів — `offline_tiles/{routeId}/` на пристрої (`OfflineMapService`).

Кожна підсистема клієнта має **власний репозиторій** і мапінг JSON → Dart-моделі (`domain`).

## 4.2. Реалізація клієнтської частини (Flutter)

### 4.2.0. Етап 5. Підключення мобільного застосунку до бекенду

У `main.dart` ініціалізується **`Supabase.initialize`** (URL і `anonKey` з `lib/core/config/supabase_config.dart`, потік **PKCE** для OAuth):

```dart
await Supabase.initialize(
  url: SupabaseConfig.url,
  anonKey: SupabaseConfig.anonKey,
  authOptions: const FlutterAuthClientOptions(
    authFlowType: AuthFlowType.pkce,
  ),
);
```

- **`supabase.auth.onAuthStateChange`** / сесія — основа для `GoRouter` (redirect на `/login` без JWT).
- **`BackendApi`** (`lib/core/api/backend_api.dart`) — єдиний вхід для Edge Functions.
- Стан UI — **flutter_riverpod**; версія застосунку **1.0.0+1** (`pubspec.yaml`).

Після підключення реалізовано модулі за принципом **feature-first** (`lib/features/`).

**Таблиця 4.1** — структура каталогів клієнта (auth, routes, navigation, trips, journal, profile, ai, `core/`).

`trip-actions`, `trip-chat`, `tripsRealtimeSyncProvider`.

### 4.2.5. Погода, журнал, профіль, ШІ

`weather`, журнал після походу, `recommend-routes`, `ai-chat`.
