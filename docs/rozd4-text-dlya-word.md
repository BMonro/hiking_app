## 4.1. Реалізація системи (поступово: від бази даних до застосунку)

У четвертому розділі подано програмну реалізацію мобільної системи **Hikora** відповідно до проєктних рішень розділу 3. Розроблення виконано **послідовними етапами**: спочатку спроєктовано та розгорнуто базу даних із політиками доступу, потім налаштовано хмарний бекенд на платформі Supabase, реалізовано серверні Edge Functions як шар BFF (Backend for Frontend), після чого до того ж проєкту підключено мобільний клієнт на Flutter. Такий порядок дозволив перевіряти кожен шар окремо (схема БД → API → UI) і забезпечити узгодженість даних між клієнтом і сервером.

---

### 4.1.1. Етап 1. База даних PostgreSQL

На першому етапі в середовищі Supabase створено реляційну базу даних **PostgreSQL**, відповідну концептуальній моделі з розділу 3. Схема містить **15 таблиць** у третій нормальній формі та одне представлення **`profile_stats`** для агрегованої статистики профілю (кількість походів, сумарна відстань і набір висоти).

Основні групи сутностей: профіль користувача (`profiles`, `profile_health_conditions`), маршрути та їх точки (`routes`, `route_points`, `route_ratings`, `saved_routes`, `offline_routes`), групові походи (`trips`, `trip_participants`, `messages`), журнал (`journal_entries`, `journal_photos`), досягнення (`achievements`, `user_achievements`) та сповіщення (`notifications`). Облікові записи зберігаються в системній таблиці **`auth.users`** (Supabase Auth); зовнішній ключ `profiles.id` посилається на `auth.users.id`.

Критичною вимогою безпеки є **Row Level Security (RLS)**: для кожної таблиці увімкнено політики, що обмежують SELECT/INSERT/UPDATE/DELETE залежно від `auth.uid()`. Наприклад, записи журналу доступні лише власнику; публічні маршрути читаються за умовою `is_public = true` або `author_id = auth.uid()`; повідомлення чату походу — лише організатору та учасникам зі статусом `approved`.

Додатково виконано:
- скрипт початкових даних **`supabase/seed_data.sql`** (тестові маршрути в Карпатах, досягнення);
- політики **Supabase Storage** для bucket `avatars` (`storage_avatars_policies.sql`);
- серверні тригери автоматичного нарахування досягнень (`achievements_auto_grant.sql`).

Після завершення цього етапу забезпечено цілісне сховище даних і серверні правила доступу без залежності від клієнтського застосунку.

---

### 4.1.2. Етап 2. Підключення бекенду (платформа Supabase)

На другому етапі схема PostgreSQL інтегрована в керований **проєкт Supabase** — окремий VPS не розгортався. Налаштовано URL проєкту та ключі доступу: **anon key** для мобільного клієнта (публічний, з захистом через RLS) та **service role** лише для адміністративних і тестових скриптів (не включається в APK).

У складі бекенду використано такі сервіси:

| Сервіс | Призначення в Hikora |
|--------|----------------------|
| PostgreSQL | Зберігання всіх бізнес-даних |
| Auth | Реєстрація, вхід email/пароль, Google OAuth, видача JWT |
| PostgREST | REST-доступ до таблиць через Supabase Dart SDK |
| Storage | Зберігання аватарів і фото журналу |
| Realtime | Підписки на зміни походів, заявок, сповіщень, чату |
| Edge Functions | Серверна бізнес-логіка та проксі до зовнішніх API |

Підключення бекенду на цьому етапі означає готовність інфраструктури: автентифікація, API до таблиць, файлове сховище та канал real-time оновлень. Клієнтський застосунок підключається до **того самого** проєкту за фіксованими `url` та `anonKey` (клас `SupabaseConfig` у Flutter).

---

### 4.1.3. Етап 3. Edge Functions (серверна бізнес-логіка, BFF)

Третій етап — реалізація **10 Edge Functions** мовою TypeScript (середовище Deno). Функції виконують роль **BFF**: мобільний клієнт не звертається напряму до OpenAI, GraphHopper, OpenWeatherMap чи Overpass із секретними ключами; усі зовнішні виклики виконуються на сервері, а ключі зберігаються в **Supabase Secrets**.

| № | Функція | Призначення |
|---|---------|-------------|
| 1 | `save-route` | Створення/оновлення маршруту, розрахунок метрик, GeoJSON |
| 2 | `route-hike` | Пішохідна маршрутизація (GraphHopper / OSRM) |
| 3 | `prepare-offline-route` | Полілінія для офлайн-пакета |
| 4 | `recommend-routes` | Персоналізовані рекомендації (OpenAI або резервний алгоритм) |
| 5 | `ai-chat` | Діалоговий ШІ-консультант |
| 6 | `weather` | Прогноз погоди (OpenWeatherMap) |
| 7 | `geosearch` | Геопошук місць |
| 8 | `poi-nearby` | POI поблизу маршруту (Overpass) |
| 9 | `trip-actions` | Створення походів, заявки, рішення організатора |
| 10 | `trip-chat` | Отримання та відправка повідомлень чату |

Кожна функція перевіряє заголовок **`Authorization: Bearer <JWT>`** і відхиляє запити без валідної сесії (HTTP 401). Приклад початку обробника `save-route`:

```typescript
const authHeader = req.headers.get("Authorization");
if (!authHeader?.startsWith("Bearer ")) {
  return jsonResponse({ error: "unauthorized" }, 401);
}
const { data: { user } } = await supabase.auth.getUser();
```

Після валідації тіла запиту функція `save-route` обчислює відстань, набір висоти та орієнтовну тривалість (`computeRouteStats`), будує трек через `fetchHikingRouteThrough` (GraphHopper або OSRM) і зберігає маршрут разом із точками в таблицях `routes` та `route_points`. Резервний варіант — лінія між waypoints, якщо зовнішній маршрутизатор недоступний.

Реалізація Edge Functions завершує **серверну** частину бізнес-логіки; далі зафіксовано правила обміну даними з клієнтом.

---

### 4.1.4. Етап 4. Контракт обміну даними (API між клієнтом і бекендом)

Четвертий етап серверної реалізації — формалізація **контракту взаємодії**, який використовує мобільний застосунок:

1. **Автентифікація** — `POST /auth/v1/token` (email/пароль або OAuth); у подальших запитах передається JWT.
2. **Табличні операції** — PostgREST через Supabase SDK у класах-репозиторіях (`RoutesRepository`, репозиторії походів, журналу тощо). Приклад фільтрації каталогу маршрутів:

```dart
dynamic query = _client.from('routes').select().eq('is_public', true);
if (search != null && search.isNotEmpty) {
  query = query.ilike('title', '%$search%');
}
query = query.order('created_at', ascending: false);
```

3. **Складні операції та зовнішні сервіси** — виклик Edge Functions через клас **`BackendApi`**, який інкапсулює `functions.invoke`, таймаут і розбір помилок.
4. **Файли** — завантаження аватара в bucket `avatars` за шляхом, узгодженим із RLS Storage.
5. **Офлайн-режим** — метадані завантаження в таблиці `offline_routes`; файли тайлів OSM і `route_path.json` — у приватному каталозі застосунку на пристрої.

Таким чином, до початку розробки інтерфейсу визначено два канали доступу до бекенду: **прямий REST до таблиць** (з урахуванням RLS) та **виклики Edge Functions** для операцій, що потребують зовнішніх API або складних обчислень.

## 4.2. Реалізація клієнтської частини (Flutter)

### 4.2.0. Етап 5. Підключення мобільного застосунку до бекенду

Клієнтська програма реалізована мовою **Dart** у фреймворку **Flutter** (SDK 3.0+, версія застосунку 1.0.0+1). На етапі підключення в `main.dart` виконується ініціалізація Supabase з параметрами з `SupabaseConfig` та потоком автентифікації **PKCE** (рекомендовано для OAuth на Android):

```dart
await Supabase.initialize(
  url: SupabaseConfig.url,
  anonKey: SupabaseConfig.anonKey,
  authOptions: const FlutterAuthClientOptions(
    authFlowType: AuthFlowType.pkce,
  ),
);
```

Після ініціалізації:
- стан авторизації відстежується через сесію Supabase Auth;
- маршрутизатор **`GoRouter`** (`lib/core/router/app_router.dart`) перенаправляє неавторизованого користувача на `/login`, а після входу через Google без заповненого поля `age` у `profiles` — на `/register?oauth=1`;
- управління станом UI здійснюється **flutter_riverpod**;
- виклики Edge Functions централізовані в **`BackendApi`**.

Структура проєкту організована за принципом **feature-first**: каталоги `lib/features/` (auth, home, routes, navigation, weather, trips, journal, profile, ai) містять шари `presentation`, `data`, `domain`; спільні компоненти — у `lib/core/` (router, theme, shell, api).

### 4.2.1. Реалізація навігації між екранами та захисту маршрутів

Навігація між екранами реалізована бібліотекою **go_router**. Усі робочі екрани застосунку (головна, маршрути, карта, групи, профіль) доступні лише за наявності активної JWT-сесії. Логіка `redirect` перевіряє `Supabase.instance.client.auth.currentSession` і при його відсутності повертає користувача на екран авторизації.

Основна оболонка — **`MainShell`** з нижньою панеллю на п’ять вкладок: Головна, Маршрути, Карта, Групи, Профіль. Дочірні маршрути (деталі маршруту, навігація, чат походу, редагування профілю) відкриваються поверх оболонки зі збереженням контексту сесії.

---

### 4.2.2. Реалізація маршрутів, геопошуку та збереження

Підсистема маршрутів включає каталог публічних маршрутів (`RoutesRepository.getRoutes` з фільтрами за складністю, типом, тривалістю, набором висоти та пошуком за назвою), екран деталей, редактор створення/редагування з типізованими точками (**start, finish, peak, water, shelter, danger, viewpoint**).

Геопошук місць виконується через Edge Function **`geosearch`** (сервіс `OsmNominatimService` на клієнті). Збереження маршруту — через **`save-route`** (метрики, `geojson`, точки). Побудова треку для навігації в онлайн-режимі — **`route-hike`** (`RoutingRepository`).

---

### 4.2.3. Реалізація офлайн-карт і навігації

Сервіс **`OfflineMapService`** реалізує метод `downloadRouteMap`, який:
- викликає **`prepare-offline-route`** для отримання полілінії;
- завантажує тайли OpenStreetMap (zoom 11–16) у каталог `offline_tiles/{routeId}/`;
- зберігає `route_path.json`, `map_meta.json` і маркер **`.complete`** після успішного завершення;
- дублює запис у таблиці **`offline_routes`**.

Реалізовано **два режими навігації**:
1. **Онлайн** — з екрана деталей маршруту: GPS, перебудова при відхиленні, POI (`poi-nearby`), fallback тайлів.
2. **Офлайн-only** — з вкладки «Офлайн» у «Мої маршрути» (`offline=true`): без мережевих запитів до API маршрутизації для цього маршруту.

На екрані **`NavigationScreen`** відображаються поточна позиція (з обертанням маркера за курсом), пройдений (сірий) і залишковий (зелений) шлях. Після завершення походу відкривається діалог збереження запису в журнал.

---

### 4.2.4. Реалізація групових походів і чату

Групові походи: створення та редагування через Edge **`trip-actions`**, заявки учасників (`apply`, `decide`, `cancel`). Список походів і статуси оновлюються через **Realtime** (`tripsRealtimeSyncProvider` — підписки на `trips`, `trip_participants`, `notifications`, `messages`).

Чат походу — Edge **`trip-chat`**; повідомлення зберігаються в `messages` з RLS (доступ лише організатору та учасникам зі статусом `approved`). Екран **`TripChatScreen`** відображає історію та форму відправки.

---

### 4.2.5. Реалізація погоди, журналу, профілю та штучного інтелекту

- **Погода:** `WeatherRepository` → Edge **`weather`** (OpenWeatherMap на сервері); екран погоди на маршруті — пакетний запит по точках.
- **Журнал:** таблиці `journal_entries`, `journal_photos`; після навігації — автоматична пропозиція створити запис.
- **Профіль:** редагування, аватар (Storage), статистика (`profile_stats`), досягнення (тригери БД), налаштування (пароль, сповіщення).
- **ШІ:** на головному екрані — **`recommend-routes`** (до 5 маршрутів, `source`: `ai` або `profile`) та **`ai-chat`**; ключ OpenAI лише в Supabase Secrets.

## 4.3. Результати реалізації (демонстрація роботи застосунку)

Після завершення етапів реалізації перевірено роботу застосунку на **Android-емуляторі** та **фізичному смартфоні**. Нижче наведено ілюстрації основних екранів; вони демонструють практичну цінність продукту, а не протокол тестування.

**Рис. 4.1 — Екран авторизації.** Користувач входить за email і паролем або через Google. До завершення автентифікації доступні лише екрани входу та реєстрації; це реалізує захист маршрутів `GoRouter` на основі JWT-сесії Supabase Auth.

**Рис. 4.2 — Головний екран.** Відображається блок персоналізованих рекомендацій маршрутів (Edge `recommend-routes`) та вбудований ШІ-консультант (`ai-chat`). Клієнт не містить секретного ключа OpenAI — запити обробляються на сервері.

**Рис. 4.3 — Каталог і деталі маршруту.** Підтримуються пошук за назвою та фільтрація за складністю, типом, тривалістю й набором висоти. На екрані деталей — метрики маршруту, точки, можливість перегляду погоди та переходу до навігації або завантаження офлайн-пакета.

**Рис. 4.4 — Екран навігації під час походу.** Карта займає основну площу екрана; відображаються поточна GPS-позиція, пройдений і залишковий трек. Режим відповідає обраному сценарію: онлайн з перебудовою маршруту або офлайн за локально збереженими тайлами.

**Рис. 4.5 — Групові походи та чат.** Список опублікованих походів з датами та організатором; учасник подає заявку, організатор схвалює або відхиляє. Після схвалення доступний чат походу в реальному часі.

**Рис. 4.6 — Журнал походів.** Після завершення навігації система пропонує зберегти запис із попередньо заповненими метриками (відстань, тривалість, набір висоти); користувач може додати нотатки та фотографії.

Демонстрація підтверджує, що реалізовані підсистеми інтегровані в єдиний сценарій: від реєстрації до планування маршруту, офлайн-підготовки, проходження походу та фіксації результатів у журналі.

## 4.4. Тестування

Тестування мобільного застосунку Hikora проведено у **три етапи**, узгоджені з методичними рекомендаціями: (1) функціональне тестування, (2) тестування безпеки зі статичним аналізом (MobSF), (3) навантажувальне тестування серверної частини. Такий порядок дозволяє спочатку підтвердити коректність бізнес-сценаріїв, потім — захищеність даних і лише після цього оцінити поведінку під навантаженням.

**Середовище:** окремий тестовий проєкт Supabase, тестові облікові записи, скрипт `seed_data.sql`, Android-емулятор і фізичний пристрій.

---

### 4.4.1. Розробка тестів

#### 4.4.1.1. Функціональні тестові випадки

Функціональні тести спроєктовано методом **чорної скриньки** на основі специфікації вимог (розділ 2). Кожен випадок містить: ідентифікатор, модуль, передумови, кроки, очікуваний результат, тестові дані.

**Таблиця 4.1** — розподіл тестових випадків за модулями (повний перелік — **Додаток Л**). Усього **63** випадки в шести модулях: автентифікація та профіль, маршрути, навігація та офлайн, групові походи, журнал, профіль і досягнення.

Приклади сценаріїв: успішна реєстрація; відмова входу з невірним паролем; створення маршруту без точки finish (валідація); завантаження офлайн-пакета та навігація без мережі; подача та схвалення заявки на похід; збереження запису журналу після завершення маршруту.

#### 4.4.1.2. Тестові випадки безпеки

Тести безпеки перевіряють **RLS**, коректність **JWT** на Edge Functions та політики **Storage**. Сформовано **37** сценаріїв (ST-01 … ST-30, ST-Storage, ST-29 тощо) згруповано в **Таблиці 4.2** (деталі — **Додаток Л**).

Для перевірки ізоляції даних використано **два** тестові облікові записи (користувачі A і B). Автоматизація частини перевірок — скрипт **`docs/run_security_tests_st.py`** (виклики REST/Edge без UI).

#### 4.4.1.3. План SAST і перевірки зберігання даних

| Перевірка | Інструмент | Об’єкт |
|-----------|------------|--------|

#### 4.4.1.4. План навантажувального тестування

Сценарій **`docs/jmeter/hikora_supabase_load.jmx`** (Apache JMeter 5.6):
- **Setup Thread Group (1 потік):** отримання JWT (`POST /auth/v1/token`), збереження `route_id`, `trip_id`;
- **Thread Group (N потоків, L циклів):** імітація роботи авторизованого клієнта — Edge Functions (`recommend-routes`, `route-hike`, `weather`, `geosearch`, `poi-nearby`, `prepare-offline-route`) та REST Supabase (маршрути, походи, учасники, чат);
- **Listeners:** Aggregate Report, Summary Report (метрики: середній час, 90-й перцентиль, % помилок, пропускна здатність).

### 4.4.2. Результати функціонального тестування *(1-й етап)*

Функціональне тестування виконано **першим** після завершення реалізації основних модулів. За **63** тестовими випадками з **Таблиці 4.1** усі перевірки завершилися **успішно** (статус «Пройдено»).

**Таблиця 4.3** — зведені результати за модулями.

Підтверджено повний цикл використання: реєстрація → заповнення профілю → перегляд каталогу → створення/редагування маршруту → завантаження офлайн-пакета → навігація (онлайн і офлайн) → груповий похід і чат → запис у журнал.

У процесі розробки виявлено та усунено дефекти, зокрема: некоректне закриття списку підказок геопошуку; відсутність обертання маркера GPS; автоматичне перемикання в офлайн-режим там, де потрібен явний вибір вкладки «Офлайн».

### 4.4.3. Результати тестування безпеки та SAST *(2-й етап)*

Тестування безпеки виконано **другим** етапом. Усі **37** сценаріїв з **Таблиці 4.2** завершилися **успішно**.

**Таблиця 4.4** — зведення за групами перевірок.

**Сервер (ST-скрипт і ручні перевірки):**
- користувач A **не** отримує доступ до `journal_entries` користувача B (RLS);
- виклик Edge Function **без** JWT повертає **401**;
- організатор керує заявками; неучасник **не** читає чат походу;
- завантаження в Storage без токена або в чужий каталог `avatars/` — **відмова** (ST-Storage-1/2);
- у клієнтському коді/APK **немає** service role key та ключів OpenAI (`sk-`) — ST-29.

**MobSF (APK `app-release.apk`):**
- мережа: **cleartext заборонено**, конфігурація HTTPS (`network_security_config`);
- **трекери відсутні**;
- дозволи (геолокація, камера, галерея) **обґрунтовані** функціями застосунку (навігація, аватар, журнал);
- публічний **anon key** Supabase у клієнті — архітектурно допустимо; захист даних — **JWT + RLS**;
- у release-збірці: `minSdk = 29`, `allowBackup=false`, підпис release-keystore, логування власного коду лише в debug (`app_log.dart`), R8 для зменшення слідів `Log` у SDK.

**flutter analyze** для `lib/` — без критичних помилок типізації (результат — **Додаток Л**).

*PDF-звіт MobSF, протоколи ST — **Додаток Л**, розділ «Безпека та SAST».*

Попередження MobSF рівня INFO про логи та clipboard у декомпільованому коді Flutter-плагінів **не** свідчать про витік паролів у коді Hikora; для полів пароля вимкнено копіювання тексту.

### 4.4.4. Результати навантажувального тестування *(3-й етап)*

Навантажувальне тестування виконано **останнім**, після підтвердження функціональності та безпеки.

**Інструмент:** Apache JMeter 5.6, план `hikora_supabase_load.jmx`, репозиторій Hikora (`docs/jmeter/`).

**Параметри прогону (для звіту):** 1000 віртуальних користувачів (паралельні потоки), сценарій імітує авторизованого клієнта після Setup (1 потік — отримання JWT).

**Рис. 4.7 — Aggregate Report JMeter.** За результатами прогону виконано **13 003** HTTP-запитів; частка помилок — **13,67%**. Операції читання даних Supabase (REST: походи, учасники, сповіщення) та автентифікація показали **нижчий** відсоток помилок; найбільше відмов — на викликах **`recommend-routes`** (зовнішній OpenAI / ліміти) та **`poi-nearby`** (Overpass), що пояснюється залежністю від сторонніх сервісів, а не збоєм RLS чи JWT.

**Таблиця 4.5** — метрики за типами запитів (середній час відгуку, 90-й перцентиль, % помилок, пропускна здатність, req/s). *Повна таблиця — під рис. 4.7 або в Додатку Л.*

**Висновок:** архітектура BFF на Supabase витримує інтенсивне звернення клієнтів до REST і більшості Edge Functions; під екстремальним навантаженням (1000 VU) вузькими місцями стають зовнішні API. Для типового використання мобільним застосунком отримані результати прийнятні; рекомендовано кешування та обмеження частоти викликів до OpenAI/Overpass у production.

## 4.6. Надійність та обмеження

**Надійність** забезпечується обробкою помилок мережі, резервним маршрутом OSRM при недоступності GraphHopper, резервним підбором маршрутів без ШІ (`rankRoutesByProfile` на сервері), маркером цілісності офлайн-пакета `.complete`.

**Обмеження версії 1.0.0:**
1. Повноцінний офлайн лише для попередньо завантажених маршрутів.
2. Онлайн-режим залежить від зовнішніх API (погода, маршрутизація, OSM).
3. Push-сповіщення (FCM) не реалізовані; сповіщення — in-app і запис у БД.
4. UI для оцінок і «збережених маршрутів» відсутній.
