РОЗДІЛ 4. РЕАЛІЗАЦІЯ ТА ТЕСТУВАННЯ МОБІЛЬНОГО ЗАСТОСУНКУ HIKORA
4.1. Реалізація серверної частини
Серверну частину застосунку розгорнуто на хмарній платформі Supabase без використання окремого VPS-сервера. База даних PostgreSQL містить 15 таблиць та одне представлення profile_stats з увімкненим механізмом Row Level Security для розмежування доступу між користувачами. Таблиці охоплюють усі сутності системи: profiles, profile_health_conditions, routes, route_points, route_ratings, saved_routes, offline_routes, trips, trip_participants, messages, journal_entries, journal_photos, achievements, user_achievements та notifications. Автентифікація реалізована через Supabase Auth з підтримкою входу через email і пароль та Google OAuth. Серверна логіка винесена в Edge Functions на базі Deno: ai-chat, recommend-routes та trip-actions.
Обмін даними між клієнтом і сервером відбувається через Supabase Dart SDK (PostgREST): репозиторії формують запити .from('table').select() / .eq() / .upsert(), результати перетворюються на Dart-моделі вручну в шарі data (патерн Repository, без ORM). Для оновлення списку походів і сповіщень використовується Supabase Realtime через WebSocket-підписки. Завантажені офлайн-маршрути дублюються записом у таблиці offline_routes, а файли пакета зберігаються у файловій системі пристрою через path_provider.
Аватари користувачів зберігаються в Supabase Storage (bucket avatars) через сервіс AvatarStorageService. Обкладинки маршрутів зберігаються як URL у полі таблиці routes. Структуру серверної частини наведено на рис. 4.1.

4.2. Реалізація клієнтської частини
Клієнтський застосунок реалізовано мовою Dart у фреймворку Flutter SDK 3.0+. Проєкт організовано за принципом feature-first: каталог lib/features/ містить окремі модулі auth, routes, navigation, weather, trips, journal, profile, ai, home. Кожен модуль поділено на три шари: presentation (екрани та віджети), data (репозиторії та сервіси) та domain (моделі). Спільна інфраструктура зосереджена в lib/core/ — конфігурація роутера, тема застосунку та оболонка з нижньою панеллю навігації. Структуру клієнтської частини подано на рис. 4.2.

4.2.1. Реалізація маршрутів та геопошуку
Каталог публічних маршрутів завантажується через RoutesRepository з фільтрацією за складністю, типом маршруту, тривалістю, набором висоти та пошуком за назвою. Точки маршруту (route_points) завантажуються окремим запитом у методі getRouteDetail, а не разом із каталогом. Нижче наведено фрагмент формування запиту до PostgREST з фільтрами.
Фрагмент репозиторію маршрутів — формування запиту до PostgREST з фільтрами
Future<List<RouteModel>> getRoutes({
String? search,
String? difficulty,
String? routeType,
double? durationMax,
int? ascentMax,
}) async {
dynamic query = _client.from('routes').select().eq('is_public', true);
if (search != null && search.isNotEmpty) {
query = query.ilike('title', '%\$search%');
}
if (difficulty != null && difficulty != 'all') {
query = query.eq('difficulty', difficulty);
}
if (routeType != null && routeType != 'all') {
query = query.eq('route_type', routeType);
}
if (durationMax != null && durationMax > 0) {
query = query.lte('duration_h', durationMax);
}
if (ascentMax != null && ascentMax > 0) {
query = query.lte('ascent_m', ascentMax);
}
query = query.order('created_at', ascending: false);
final data = await query;
return (data as List).map((json) => RouteModel.fromJson(json)).toList();
}
Пошук назв місць реалізовано через OsmNominatimService (Nominatim та Overpass API для вершин). HTTP-запити до GraphHopper, OSRM та OpenWeatherMap виконуються через бібліотеку Dio. Метрики маршруту обчислюються локально за координатами точок, а лінія уточнюється через GraphHopper API (профіль hike) або OSRM як резерв.
4.2.2. Реалізація офлайн-карт та навігації
Сервіс OfflineMapService реалізує метод downloadRouteMap, який повертає потік прогресу OfflineMapDownloadProgress. У каталозі offline_tiles/{routeId} зберігаються тайли OpenStreetMap (рівні масштабу 11–16), файл лінії route_path.json, метадані map_meta.json та маркер .complete. Після завершення завантаження запис про офлайн-маршрут дублюється в таблиці offline_routes. Нижче наведено фрагмент завантаження пакета.

Після завантаження пакета запис зберігається також у БД через upsert у таблицю offline_routes із полями user_id, route_id, downloaded_at та tile_cache_mb. Реалізовано два режими навігації: класична онлайн-навігація з екрана деталей маршруту (з перебудовою треку та шаром POI) та офлайн-only режим, що запускається з Профіль → Мої маршрути → вкладка «Офлайн» з параметром offline=true. На екрані навігації відображається поточна позиція GPS з обертанням маркера за курсом, пройдена частина маршруту (сірий колір) та залишкова (зелений). При відхиленні в онлайн-режимі система показує SnackBar та автоматично перебудовує трек. Результат роботи навігаційного екрану наведено на рис. 4.3.

4.2.3. Реалізація ШІ-функціоналу
Модуль штучного інтелекту реалізовано через Edge Function recommend-routes, яка повертає список recommendations (ідентифікатор маршруту та текстове обґрунтування) і поле source (ai або profile). Клієнтський AiService викликає функцію без передачі user_id у тілі запиту — автентифікація виконується за JWT. Далі personalizedRoutesProvider завантажує повні картки маршрутів через getRoutesByIds. Ключ OPENAI_API_KEY зберігається виключно в Supabase Secrets. За його відсутності сервер повертає source: profile і список від резервного алгоритму rankRoutesByProfile. Нижче наведено фрагмент виклику Edge Function.

4.2.4. Реалізація групових походів
Створення походу реалізовано через форму з вибором маршруту, дат, опису та ліміту учасників. Заявки учасників та рішення організатора обробляються Edge Function trip-actions з діями apply, decide та cancel. Список походів оновлюється в реальному часі через Supabase Realtime. Груповий чат зберігається в таблиці messages з доступом лише для учасників зі статусом approved через RLS-політики. Модуль групових походів доступний через вкладку Групи нижньої панелі навігації.
4.3. Результати реалізації застосунку
Після реалізації застосунку проведено перевірку роботи всіх функціональних модулів на Android-пристрої. Екран авторизації підтримує вхід через email та Google (рис. 4.4). Після першої реєстрації користувач потрапляє на екран налаштування профілю, де вказує вік, рівень підготовки та медичні обмеження.
Рис. 4.4. Екран авторизації застосунку
На головному екрані відображається блок персоналізованих рекомендацій маршрутів та вікно ШІ-консультанта (рис. 4.5). Рекомендації підбираються відповідно до профілю користувача; при відсутності ключа OpenAI джерело рекомендацій — алгоритм ранжування за профілем (source: profile).
Рис. 4.5. Головний екран з рекомендаціями та ШІ-консультантом
Каталог маршрутів підтримує пошук за назвою та фільтрацію за складністю, типом маршруту, тривалістю та набором висоти. При відкритті деталей маршруту відображається інтерактивна карта з треком, перелік ключових точок та кнопки завантаження офлайн-пакета і початку навігації (рис. 4.6).

4.4.1. Розробка тестів

Додатково проведено тестування інтерфейсу, безпеки та статичний аналіз коду командою flutter analyze. Для перевірки RLS-політик використано окремий тестовий проєкт Supabase. Тестові дані завантажено через скрипт supabase/seed_data.sql. Детальний опис тестових випадків подано в додатку Л.

4.4.2. Виявлені та усунені дефекти
У процесі тестування виявлено три дефекти, які усунено до завершення розробки.
Дефект №1. Некоректне закриття списку підказок OSM після вибору місця на екрані погоди та при створенні точок маршруту. Причина: відсутність виклику FocusScope.unfocus() після вибору елемента. Усунено додаванням відповідного виклику в обробник події вибору.
Дефект №2. Відсутність обертання маркера GPS на карті відповідно до напрямку руху. Причина: не передавалось значення heading з потоку geolocator. Усунено передачею параметра курсу до віджету маркера.
Дефект №3. Некоректний автоматичний перехід в офлайн-режим при наявності завантаженого пакета навіть за наявності мережі. Усунено розділенням класичної та офлайн-навігації на два окремі режими із явним вибором користувача.
4.5. Висновки до розділу
У четвертому розділі описано програмну реалізацію мобільного застосунку Hikora та наведено результати тестування. Реалізовано сім ключових підсистем: автентифікацію з профілем, каталог маршрутів із геопошуком, офлайн-навігацію з двома режимами роботи, моніторинг погоди, групові походи з оновленнями в реальному часі, ШІ-рекомендації та журнал з досягненнями. Серверну частину розгорнуто на Supabase (15 таблиць, одне представлення) без окремого VPS.
Проведено функціональне тестування за 12 тестовими випадками, тестування безпеки та орієнтовне тестування продуктивності. Усі функціональні вимоги специфікації розділу 2 підтверджено. У поточній версії не реалізовано інтерфейс оцінювання маршрутів (route_ratings) та збережених маршрутів (saved_routes), хоча відповідні таблиці є в БД. Мобільні push-сповіщення (FCM) не використовуються; події походів доставляються через запис у notifications та оновлення UI засобами Realtime і SnackBar. Детальні протоколи тестування та скріншоти екранів наведено в додатку Л, інструкція користувача — в додатку М.
