РОЗДІЛ 4. РЕАЛІЗАЦІЯ ТА ТЕСТУВАННЯ МОБІЛЬНОГО ЗАСТОСУНКУ HIKORA
4.1. Реалізація серверної частини
Серверну частину застосунку розгорнуто на хмарній платформі Supabase [12] без використання окремого VPS-сервера. База даних PostgreSQL [13] містить 15 таблиць та одне представлення profile_stats з увімкненим механізмом Row Level Security [16]. Автентифікацію реалізовано через Supabase Auth з підтримкою входу через email і пароль та Google OAuth. Серверна логіка, що потребує захищеного доступу до зовнішніх API або атомарного виконання операцій, реалізована через 10 Edge Functions на базі Deno, які відіграють роль BFF-шару між мобільним клієнтом і зовнішніми постачальниками даних.
4.1.1. Реалізація серверних функцій
Серверні функції виконують роль BFF-шару між мобільним клієнтом і зовнішніми сервісами. Кожна функція приймає запит від клієнта, виконує необхідну логіку на сервері та повертає результат. Ключ OPENAI_API_KEY та інші секрети зберігаються виключно в Supabase Secrets і не потрапляють у клієнтський код, що відповідає вимозі безпеки специфікації.
Функція save-route виконує обчислення метрик маршруту та побудову GeoJSON-треку через GraphHopper [21] або OSRM. Для обчислення відстані між координатами застосовано формулу гаверсинуса, яка враховує кривизну Землі та забезпечує точність обчислень для великих відстаней. Паралельно обчислюються сумарний підйом та орієнтовна тривалість проходження. Уривок коду функцій обчислення метрик маршруту (supabase/functions/_shared/routing.ts):
function haversineM(a: LatLng, b: LatLng): number {
const R = 6371000;
const dLat = ((b.lat - a.lat) * Math.PI) / 180;
const dLon = ((b.lon - a.lon) * Math.PI) / 180;
const lat1 = (a.lat * Math.PI) / 180;
const lat2 = (b.lat * Math.PI) / 180;
const x =
Math.sin(dLat / 2) ** 2 +
Math.cos(lat1) * Math.cos(lat2) * Math.sin(dLon / 2) ** 2;
return 2 * R * Math.asin(Math.sqrt(x));
}
export function computeRouteStats(points) {
let meters = 0; let ascent = 0;
for (let i = 1; i < coords.length; i++) {
meters += haversineM(coords[i-1], coords[i]);
const diff = (cur.altitude_m ?? 0) - (prev.altitude_m ?? 0);
if (diff > 0) ascent += diff;
}
const km = meters / 1000;
const durationH = km / 4 + ascent / 600;
return { distance_km: Math.round(km*100)/100,
ascent_m: ascent,
duration_h: Math.round(durationH*10)/10 };
}

Результат зберігається у полі geojson_track типу JSONB в таблиці routes. Якщо зовнішній сервіс маршрутизації недоступний, геометрія формується безпосередньо з координат вузлових точок. Маршрутизацію реалізовано з ланцюгом резервних варіантів: GraphHopper → OSRM → побудова по сегментах. Така стратегія забезпечує стійкість до недоступності окремих зовнішніх сервісів без переривання процесу збереження маршруту. Уривок коду функції fetchHikingRouteThrough, що реалізує ланцюг резервування (supabase/functions/_shared/routing.ts):
export async function fetchHikingRouteThrough(waypoints) {
if (waypoints.length < 2) return { points: [], source: 'none' };
const key = ghKey();
if (key) {
try {
const pts = await graphHopperRoute(waypoints);
return { points: pts, source: 'graphhopper' };
} catch (_) { /* перехід до OSRM */ }
}
try {
const pts = await osrmFootRoute(waypoints);
return { points: pts, source: 'osrm' };
} catch (_) { /* перехід до сегментів */ }
const pts = await chainLegRoutes(waypoints);
return { points: pts, source: key ? 'chain' : 'osrm_chain' };
}

Резервний алгоритм rankRoutesByProfile ранжує маршрути на основі числових показників: відповідності рівня складності, близькості тривалості до уподобаної, а також досвіду користувача. Кожен критерій має власну вагу, що дозволяє формувати змістовні рекомендації навіть без доступу до OpenAI. Уривок коду алгоритму ранжування (supabase/functions/_shared/route_ranking.ts):
export function rankRoutesByProfile(profile, routes, limit = 5) {
const fitness = profile?.fitness_level ?? 'beginner';
const targetDiff = profile?.preferred_difficulty
?? difficultyFromFitness(fitness);
const scored = [];
for (const route of routes) {
let score = 0; const parts = [];
const diffScore = difficultyScore(targetDiff, route.difficulty);
score += diffScore * 40;
if (diffScore > 0.7) parts.push('відповідає вашій складності');
if (prefDuration && route.duration_h > 0) {
const ratio = route.duration_h / prefDuration;
if (ratio <= 1.15) { score += 25; parts.push('комфортна тривалість'); }
else if (ratio <= 1.4) score += 10;
else score -= 15;
}
if (experience < 3 && route.difficulty === 'easy') score += 15;
scored.push({ route, score, reason: parts.join(', ') || '...' });
}
return scored.sort((a,b) => b.score - a.score)
.slice(0, limit).map(e => ({ route_id: e.route.id, reason: e.reason }));
}
Функція prepare-offline-route будує полілінію для офлайн-пакета через fetchHikingRouteThrough з резервом із GeoJSON маршруту або прямих waypoints. Функції trip-actions та trip-chat обробляють відповідно заявки групових походів і повідомлення чату, забезпечуючи серверну валідацію бізнес-правил, які не можна перевірити на рівні RLS.
4.1.2. Реалізація доступу до даних
Обмін даними між клієнтом і базою відбувається через Supabase Dart SDK (PostgREST) за патерном Repository [14] без ORM. Кожна підсистема має власний клас репозиторію, що приховує деталі формування запитів і перетворює результати на об'єкти предметної галузі. Такий підхід відповідає принципу єдиної відповідальності та спрощує тестування окремих компонентів. Для синхронізації даних у реальному часі використовуються WebSocket-підписки Supabase Realtime на таблиці trips, trip_participants, notifications та messages.
Аватари зберігаються в Supabase Storage (bucket avatars) через сервіс AvatarStorageService. Завантажені офлайн-маршрути дублюються записом у таблиці offline_routes, а файли пакета зберігаються у файловій системі пристрою через path_provider. Уривок коду запису метаданих офлайн-завантаження в БД (lib/features/routes/data/routes_repository.dart):
await _client.from('offline_routes').upsert({

Операція upsert гарантує відсутність дублювання записів при повторному завантаженні пакета для того самого маршруту. Завдяки увімкненому RLS [16] запит автоматично застосовує фільтр user_id, що відповідає ідентифікатору поточного JWT-токену.
4.2. Реалізація клієнтської частини
Клієнтський застосунок реалізовано мовою Dart у фреймворку Flutter SDK 3.0+ [11]. Проєкт організовано за принципом feature-first: каталог lib/features/ містить модулі auth, routes, navigation, weather, trips, journal, profile, ai, home. Кожен модуль поділено на шари presentation, data та domain. Спільна інфраструктура зосереджена в lib/core/ і охоплює маршрутизатор, обгортку викликів серверних функцій, тему оформлення та валідатори форм. Управління станом реалізовано бібліотекою flutter_riverpod [23], навігацію — через go_router [24]. Структуру клієнтської частини наведено у додатку Б.
4.2.1. Реалізація навігації та захисту маршрутів
Навігацію між екранами реалізовано через go_router [24] із захистом маршрутів на основі стану JWT-сесії. Маршрутизатор перевіряє наявність активного токену та заповненість фізичного профілю після кожної зміни стану автентифікації. Якщо користувач увійшов через Google OAuth, але не заповнив профіль (поле age відсутнє в таблиці profiles), він перенаправляється на /register?oauth=1 для завершення реєстрації. Без цієї перевірки алгоритм рекомендацій не матиме достатньо даних для формування персоналізованого списку. Уривок коду функції redirect (lib/core/router/app_router.dart):

Перевірку заповнення профілю реалізовано окремою асинхронною функцією, яка виконує запит поля age до таблиці profiles. Якщо запис відсутній або age = null, функція повертає true, що ініціює перенаправлення. Уривок коду (lib/core/router/app_router.dart):
Future<bool> _needsPhysicalProfile(String userId) async {
final profile = await Supabase.instance.client
.from('profiles')
.select('age')
.eq('id', userId)
.maybeSingle();
return profile == null || profile['age'] == null;
}

4.2.2. Реалізація маршрутів, геопошуку та збереження
Каталог публічних маршрутів завантажується через RoutesRepository з динамічним формуванням запиту до PostgREST залежно від встановлених фільтрів. Фільтри за складністю, типом маршруту (circular / linear / radial / combined), тривалістю та набором висоти застосовуються лише тоді, коли відповідний параметр переданий і не дорівнює значенню «усі». Завдяки цьому не надсилаються зайві умови до бази даних. Точки маршруту завантажуються окремим запитом у методі getRouteDetail, а не разом із каталогом, що зменшує обсяг даних при першому завантаженні списку. Уривок коду формування запиту (lib/features/routes/data/routes_repository.dart):
dynamic query = _client.from('routes').select().eq('is_public', true);
if (search != null && search.isNotEmpty)
query = query.ilike('title', '%$search%');
if (difficulty != null && difficulty != 'all')

query = query.eq('route_type', routeType);

Геопошук назв місць і вершин для редактора маршруту виконується через Edge Function geosearch, яка звертається до Nominatim та Overpass API. Завдяки виконанню геопошуку на сервері клієнт не взаємодіє з цими API безпосередньо, а запити йдуть від IP-адреси Supabase, що дозволяє уникнути обмежень за частотою запитів. Побудова лінії маршруту відбувається через Edge Function route-hike, яка застосовує профіль hike у GraphHopper [21] для пішохідних стежок. У разі недоступності Edge Function RoutingRepository як резерв звертається до API маршрутизації безпосередньо через Dio. Збереження маршруту разом із точками виконується атомарно через Edge Function save-route, що гарантує цілісність даних навіть у разі часткового збою.

Сервіс OfflineMapService реалізує метод downloadRouteMap, що повертає потік прогресу OfflineMapDownloadProgress. Тайли завантажуються пакетами по 6 через Dio для забезпечення паралельності без перевантаження з'єднання. Цей підхід дозволяє перервати завантаження і відновити його пізніше, перевіряючи наявність вже збережених тайлів. Метадані пакета та лінія маршруту зберігаються в окремих файлах у каталозі offline_tiles/{routeId}. Реалізовано два режими навігації. Класична онлайн-навігація запускається з екрана деталей маршруту і підтримує перебудову треку при відхиленні через route-hike та відображення точок інтересу через poi-nearby. Офлайн-only режим запускається з вкладки «Офлайн» у «Мої маршрути» з параметром offline=true і не виконує жодних мережевих запитів, використовуючи виключно локальні тайли та збережену лінію маршруту. На навігаційному екрані маркер поточної позиції обертається відповідно до значення heading з потоку geolocator, що відображає напрямок руху. Пройдена частина маршруту відображається сірим кольором, залишкова — зеленим. При відхиленні понад пороговий показник в онлайн-режимі система відображає SnackBar-повідомлення і автоматично ініціює перебудову треку. Перебудова треку виконується лише при відхиленні понад 75 м або після двох послідовних вимірювань з відхиленням понад 45 м. Такий двопорогований підхід запобігає надмірній кількості запитів до API маршрутизації при незначних відхиленнях, наприклад при обході перешкоди.
4.2.4. Реалізація групових походів
Створення та управління походом реалізовано через Edge Function trip-actions, яка виконує серверну перевірку бізнес-правил, недоступних на рівні RLS. Зокрема, перевіряється, що організатор не може подати заявку на власний похід, а кількість учасників не перевищує встановлений ліміт. Заявки та рішення організатора обробляються з діями apply, decide та cancel. Уривок коду створення групового походу (lib/features/trips/data/trips_api.dart):

Повідомлення чату надсилаються через Edge Function trip-chat і зберігаються в таблиці messages з RLS-доступом виключно для підтверджених учасників та організатора. Це унеможливлює читання або надсилання повідомлень користувачами зі статусом pending або rejected. Список походів та нові повідомлення оновлюються через Supabase Realtime без необхідності перезапуску застосунку.
4.2.5. Реалізація погоди, журналу та профілю
WeatherRepository викликає Edge Function weather, яка звертається до OpenWeatherMap на сервері. Виконання запиту на сервері приховує ключ API від клієнтського коду та дозволяє кешувати відповіді між запитами різних користувачів. За недоступності Edge Function використовується резервний прямий виклик OpenWeatherMap через Dio. Доступні два екрани погоди: загальний за містом або координатами та деталі погоди для конкретного маршруту. Уривок коду запиту погоди за координатами (lib/features/weather/data/weather_repository.dart):
final data = await _api.invoke(
'weather',
body: {'action': 'both', 'lat': lat, 'lon': lon},
);
Журнал реалізовано через таблиці journal_entries та journal_photos. Після завершення навігації система автоматично відкриває діалог збереження запису з попередньо заповненими метриками (фактична відстань, тривалість, підйом). Користувач може доповнити запис нотатками та фотографіями з галереї пристрою. Кількість фотографій обмежена п'ятьма — відповідна кнопка стає недоступною після досягнення ліміту.
Профіль охоплює редагування особистих даних, агреговану статистику через представлення profile_stats, досягнення з автонарахуванням тригерами в БД при досягненні порогових показників, налаштування застосунку та вкладку «Мої маршрути» з офлайн-пакетами. Вхід через Google OAuth реалізовано через Supabase Auth. Уривок коду (lib/features/auth/presentation/login_screen.dart):
final launched = await Supabase.instance.client.auth.signInWithOAuth(
OAuthProvider.google,
redirectTo: kIsWeb ? null : 'io.supabase.flutter://login-callback/',
);

4.4.5. Метрики покриття та критерій прийняття
Функціональними тестами охоплено всі варіанти використання специфікації розділу 2. Тестуванням безпеки перевірено всі чотири групи вразливостей: розмежування доступу, валідація, типові атаки та безпека файлів. Виявлені у процесі тестування три дефекти усунено до завершення розробки:
–	некоректне закриття списку підказок OSM після вибору місця — усунено додаванням FocusScope.unfocus() в обробник події вибору;
–	відсутність обертання маркера GPS відповідно до напрямку руху — усунено передачею параметра heading з потоку geolocator до віджету маркера;
–	некоректний автоматичний перехід в офлайн-режим за наявності активного мережевого з'єднання — усунено розділенням класичної та офлайн-навігації на два окремі режими із явним вибором користувача.
Критеріями успішного завершення тестування визначено такі умови:
–	усі заплановані тестові випадки функціонального тестування та тестування безпеки розроблено та виконано;
–	усі варіанти використання специфікації покриті функціональними тестами;
–	виявлені під час тестування дефекти усунено або визнано некритичними.
Усі визначені критерії виконано повною мірою. Критичних дефектів не виявлено.
4.5. Висновки до розділу 4
У четвертому розділі описано реалізацію та тестування мобільного застосунку Hikora. Серверну частину розгорнуто на Supabase з 10 Edge Functions як BFF-шаром. Реалізовано обчислення метрик маршруту за формулою гаверсинуса, ланцюг маршрутизації GraphHopper → OSRM → сегменти, резервний алгоритм ранжування маршрутів за профілем та офлайн-завантаження тайлів OSM пакетами з відстеженням прогресу. Клієнтську частину реалізовано на Flutter за принципом feature-first з трирівневою архітектурою шарів. Реалізовано вісім підсистем: автентифікацію з перевіркою профілю, маршрути з геопошуком та атомарним збереженням, офлайн-навігацію з двопороговим алгоритмом перебудови треку, погоду, групові походи з Realtime-синхронізацією, ШІ-рекомендації та резервний алгоритм, журнал і досягнення.
Проведено функціональне тестування (63 випадки у 6 модулях), тестування безпеки (37 випадків у 4 групах) та орієнтовне тестування продуктивності. Усі вимоги специфікації підтверджено, виявлені три дефекти усунено. У поточній версії не реалізовано UI для route_ratings та saved_routes; мобільні push-сповіщення через FCM не використовуються. Детальні тестові випадки наведено у додатках М та Н, інструкція користувача — у додатку Л.

Л.2. Встановлення програмного забезпечення
Для Android завантажте APK-файл за посиланням розробника та дозвольте встановлення з невідомих джерел у налаштуваннях пристрою. Для iOS встановлення виконується через TestFlight або App Store. Після встановлення надайте застосунку необхідні дозволи:
–	геолокація — для GPS-навігації (рекомендовано «Завжди» для фонового відстеження);
–	камера та галерея — для фотографій у журналі та аватара профілю.
Л.3. Налаштування програмного забезпечення
Після першого запуску виконайте такі кроки для налаштування застосунку:
–	оберіть спосіб реєстрації — через email та пароль або через обліковий запис Google;
–	заповніть фізичний профіль — вік, рівень підготовки, кількість попередніх походів, медичні обмеження та уподобання щодо складності й тривалості маршрутів;
–	за бажанням завантажте аватар у розділі редагування профілю.
Налаштування типів сповіщень доступні в розділі «Налаштування». Дані профілю впливають на якість ШІ-рекомендацій — їх рекомендується заповнити максимально точно.
Л.4. Базові функції програмного забезпечення
Л.4.1. Планування маршруту
Для підбору готового маршруту перейдіть до вкладки «Маршрути» та скористайтесь пошуком за назвою або фільтрами. При відкритті деталей маршруту відображається інтерактивна карта з треком, перелік ключових точок, метрики та прогноз погоди.
Для створення власного маршруту натисніть кнопку додавання у каталозі. В редакторі вкажіть точки маршруту, скористайтесь геопошуком для знаходження назв місць і вершин. Система автоматично розрахує протяжність, підйом та орієнтовний час через алгоритм маршрутизації.
Л.4.2. Завантаження офлайн-карти
Відкрийте деталі маршруту та натисніть «Завантажити карту офлайн». Завантаження включає тайли карти для рівнів масштабування 11–16 та лінію маршруту. Після завершення маршрут з'явиться у вкладці «Офлайн» розділу «Мої маршрути». Обсяг завантаження залежить від розміру маршруту і зазвичай складає від кількох до кількох десятків мегабайт.
Л.4.3. Навігація
Для онлайн-навігації натисніть «Почати проходження» на екрані деталей маршруту. Маркер поточної позиції обертається за напрямком руху. При відхиленні від маршруту більш ніж на 75 м система автоматично перебудовує трек. Для офлайн-навігації перейдіть до Профіль → Мої маршрути → «Офлайн» та оберіть маршрут. Після завершення система запропонує зберегти запис у журнал із заповненими метриками.
Л.4.4. Групові походи
Для організації походу перейдіть до вкладки «Групи» та натисніть кнопку створення. Заповніть форму: оберіть маршрут, вкажіть дати, місце збору, опис та ліміт учасників. Після публікації охочі можуть подавати заявки. Організатор переглядає профілі заявників та ухвалює рішення. Підтверджені учасники отримують доступ до групового чату з оновленнями в реальному часі.
Л.4.5. Журнал та статистика
Після завершення навігації система автоматично пропонує зберегти запис у журнал з попередньо заповненими метриками. Додайте нотатки, опис погодних умов та до 5 фотографій. Записи відображаються у хронологічному порядку. Статистика (кількість походів, сумарна відстань та підйом) оновлюється автоматично і відображається на екрані профілю. Досягнення нараховуються автоматично при досягненні порогових показників активності.
